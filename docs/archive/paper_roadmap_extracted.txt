Standalone Research Roadmap for a Publishable
        Agent Memory Defense Paper
Abstract
The strongest two-week paper is not another attack paper and not another vector-store-
only RAG defense. It is a compact, defense-first systems paper that asks a sharper question:
can a single, framework-agnostic runtime layer reduce poisoned writes, unsafe retrieval,
contradiction-induced failures, and cross-agent propagation across several agent memory
subsystems without destroying utility or scalability? That paper is independently
publishable because the public literature is now rich enough to define the problem, but still
fragmented enough that a clear cross-subsystem defense with real framework adapters and
scalability evidence would fill an obvious gap. Public work already documents modular
agent memory architectures, persistent memory stacks, and multiple attack families
spanning indirect prompt injection, RAG poisoning, long-term memory injection, and multi-
agent propagation. [1]
The best paper direction is a memory firewall that operates on the write path, the
retrieval path, and the propagation path. The core claim should be modest but meaningful:
a provenance-aware, quarantine-capable, risk-gated memory middleware can materially
lower unsafe retrieval and propagation across public agent frameworks and four stable
memory subsystems—vector/RAG memory, semantic fact memory, episodic/example
memory, and shared coordination memory—while preserving clean-task success and
exhibiting controlled scaling as memory size and agent count grow. That is a far better
short-paper contribution than trying to invent a novel attack, a new benchmark from
scratch, or a heavyweight formal system you cannot finish by May 16. [2]

The research problem should be stated exactly like this: modern LLM agents
increasingly treat memory as a writable runtime subsystem rather than a passive
retrieval index, but current defenses are fragmented across corpus filtering,
prompt separation, or tool-time checks; there is no compact, public, cross-
framework demonstration that one middleware layer can make memory writes,
memory retrieval, and memory propagation simultaneously safer across multiple
memory types.
That makes the paper independently publishable because the novelty is not “memory can
be attacked.” Public work already established that. The publishable unit is instead: a
reusable defense architecture plus a public, cross-framework, scalability-first
evaluation. The paper stands on public sources alone and does not need any private
benchmark, unpublished baseline, or unpublished scenario to make sense. [3]
This is also not merely a hidden rewrite of your private draft, by construction. The paper’s
contribution is defined against public frameworks, documented public memory interfaces,
public threat models, and new generic metrics. It should not reuse any unpublished attack
narrative, private metric, or draft-specific setup. If you keep the title, threat model,
scenarios, metrics, and baselines within the public space outlined below, reviewers can
evaluate the paper without knowing anything about the private draft.

Why this defense problem is timely
The defense problem is timely because the public agent ecosystem now exposes durable
memory primitives as first-class features. LangGraph distinguishes short-term and long-
term memory and explicitly discusses semantic, episodic, and procedural memory;
LlamaIndex exposes a Memory class with FIFO short-term state and long-term memory
blocks; CrewAI documents unified memory with semantic, recency, and importance
scoring plus shared and scoped views; AutoGen exposes explicit memory query,
update_context, and add interfaces; and Letta/MemGPT uses core, archival, recall, and
shared memory abstractions. In other words, the architecture trend is moving toward
more writable state, more retrieval, and more cross-session persistence, not less. [4]
At the same time, public security work already spans the relevant threat surface: indirect
prompt injection through retrieved data, poisoning of RAG corpora, backdoor-style
poisoning of memory or knowledge bases, query-only memory injection, self-reinforcing
persistent compromise through long-term memory, and cross-agent infection dynamics.
Benchmarks such as InjecAgent, AgentDojo, and Agent Security Bench show that these
failures are not toy-only phenomena and that many current defenses remain brittle or
narrowly scoped. That is exactly why a defense-first memory middleware paper is
timely now. [5]

Novelty and research gaps
Core novelty
The paper’s novelty should be stated in one precise paragraph:
      MemSieve is a framework-agnostic defense pipeline that treats agent memory as
      a write–retrieve–propagate system rather than only a retriever or a prompt. It
      normalizes heterogeneous memory records into a common schema with
      provenance, trust priors, contradiction signals, and lineage edges; validates or
      quarantines records at write time; reranks and diversifies candidates at retrieval
      time using risk-aware scoring; rewrites retrieved context into typed, provenance-
      marked evidence before reasoning; and blocks memory-conditioned tool actions
      or agent-to-agent propagation when support is weak, contradictory, or
      quarantine-tainted. The novelty is therefore the combination of cross-
      subsystem defense coverage, public framework adapters, generic defense
      metrics, and central scalability evaluation, not a new attack or a model-
      specific filter.
That novelty is real because current public work is split into disconnected islands. One
island covers memory architectures and agent design; another covers attacks such as RAG
poisoning, memory injection, and multi-agent infection; another covers inference-time
defenses such as provenance cueing, structured queries, task-alignment gating, or
traceback of poisoned RAG documents. What public work still does not provide is a
compact, cross-framework demonstration that one lightweight layer can secure multiple
memory subsystems and propagation paths under realistic scale pressures. [6]

The harsh reviewer view is simple: if the paper only shows vector-store filtering, it will read
as “another RAG defense.” If it only shows propagation in a tiny team, it will read as
synthetic. The differentiator is breadth across memory subsystems plus disciplined
scalability evidence.

Defense design
Threat model to freeze early
Use a crisp, public threat model and do not let it balloon.
The attacker should have four realistic capabilities, all already represented in public work:
query-only write inducement that causes the agent to store malicious or misleading
memory; corpus or passage poisoning of a retrievable memory source; indirect
prompt injection through retrieved or tool-returned content; and compromised
peer-agent output that gets written into shared or coordination memory. These
capabilities are grounded in prior public work on indirect prompt injection, PoisonedRAG,
AgentPoison, MINJA, Prompt Infection, and Zombie Agents. [12]
Keep the out-of-scope list short and explicit: model-weight poisoning, host compromise,
embedding-model attacks, covert channels, prompt leakage from vendor internals, and
human-in-the-loop social engineering. If you do not freeze scope, reviewers will say the
threat model is vague.

Memory subsystems to cover
Do not try to cover every conceivable memory category. The strongest paper covers four
subsystems and treats procedural/scratchpad memory as an extension, not the MVP core.

The key design choice is to avoid a monolithic learned detector. That is a schedule trap
and a review trap. Use interpretable, calibratable features plus optional second-pass
LLM checks only where necessary. In two weeks, the paper wins on architecture and
evaluation discipline, not on a fancy classifier.

What each stage should do
At write time, MemSieve should assign a source trust prior by origin: seeded system
memory and curated corpus sources start high; user free text, web retrievals, tool outputs,
and peer-agent summaries start lower; recursively summarized content receives decayed
trust. It should also scan for instructionality, policy-edit language, near duplicates, and
contradictions against high-trust semantic memory. High-risk records go to quarantine;
medium-risk records stay committed but marked low-trust; low-risk records are committed
normally.
At retrieval time, MemSieve should refuse to treat similarity as enough. It should retrieve
candidates from the native framework, but rerank them by trust, corroboration,
contradiction penalties, lineage penalties, and diversity constraints. This is where you make
the paper feel different from “just another filter.” A reviewer should be able to see that
retrieval now optimizes task utility under risk, not cosine similarity alone.
Before reasoning, retrieved memory should be transformed into structured evidence. The
agent should see that some memory is “trusted factual memory,” some is “episodic
example memory,” some is “shared note from another agent,” and some is “flagged
contradictory or quarantined.” Low-trust content should enter as data to reason about, not
as instructions to follow.
Before tool execution, the defense should verify that high-impact tool arguments are
supported by either explicit user intent or corroborated trusted memory. If the action
depends only on low-trust memory, the system should confirm or abstain. This keeps the
contribution defense-first rather than retrieval-only.
For multi-agent propagation, every shared-memory write or inter-agent summary
should carry parent record IDs and source trust. Trust should decay across summarization
hops. Rapid fan-out of a low-trust claim should trigger a freeze or quarantine. That is how
you convert “propagation” from hand-wavy rhetoric into a measurable systems claim.

Why the design generalizes across frameworks
The generalization argument must be implementation-based, not philosophical. LangGraph
documents       short-term       and      namespace        long-term memory       with
semantic/episodic/procedural framing; LlamaIndex documents explicit short-term and
long-term memory objects; CrewAI exposes shared, scoped, and sliced memory with
composite scoring; AutoGen exposes memory query, add, and update_context; and
Letta/MemGPT exposes core, archival, and shared memory paths. That means a thin
middleware adapter is realistic across public stacks. [14]

Experimental and scalability plan
Minimum publishable experiment set
The minimum publishable paper is not huge. It is:

   •     Three frameworks: LangGraph, LlamaIndex, CrewAI.
   •     Four subsystems: vector/RAG, semantic, episodic, shared coordination.
   •     Four defense settings: no defense, provenance-only, spotlighting-style retrieval
         wrapper, trust-threshold sanitizer, and full MemSieve.
   •     Four scenario families: poisoned fact insertion, retrieved instruction hijack,
         conflict/recency collision, shared-memory cascade, plus flooding as the main stress
         test.
   •    One primary model: use one low-cost but capable hosted model for the full
        matrix.
   •    One optional transfer model: only after the main figures are complete.
   •    Three random seeds or retrieval randomizations where applicable.
   •    A clean utility suite and a scalability suite.
That is enough for a short paper if the results are clean.
The strongest implementation order is:
   1.   LangGraph + vector/semantic memory + write gate + retrieval gate
   2.   CrewAI shared memory + propagation controller
   3.   LlamaIndex episodic/long-term blocks
   4.   Metric logging and lineage graph
   5.   Only then optional AutoGen
What can be simplified:

   •    Use one shared embedding backend across all frameworks.
   •    Use deterministic stub tools and auto-gradable tasks.
   •    Use a single canonical record schema everywhere.
   •    Use one public corpus family plus synthetic conflict injection rather than many
        domains.
   •    Keep the primary experimental emphasis on attack and defense, not absolute task
        intelligence.
What must not be skipped:

   •    A clean-task utility table
   •    An ablation table
   •    A propagation experiment
   •    A real scalability section
   •    At least one non-RAG subsystem result in the main paper

Stronger optional experiment set
If time holds, the strongest upgrades are:

   •    Add AutoGen as a fourth framework.
   •    Add one Letta/MemGPT-style archival/shared-memory case if integration is
        painless.
   •    Add a second model for transfer robustness.
   •    Run a small AgentDojo or ASB-inspired subset only if it plugs in cleanly on day
        one; otherwise cite those benchmarks for positioning and move on. [26]
   •      Add optional comparisons to RAGForensics on vector rows and Task Shield on
          tool rows if their code is easy to reuse. [27]
Do not attempt:

   •      StruQ reproduction
   •      New model training
   •      Full AgentDojo integration from scratch
   •      A new benchmark from scratch
   •      Human evaluation
   •      A fifth framework

What results would actually convince reviewers
For a short paper, the following would be convincing:
    •   At least 60–80% relative reduction in unsafe retrieval or attack success on three
        or more scenario families.
    •   At most 5–10% clean-task loss on the main clean utility table.
    •   A propagation result where contamination depth or fan-out is sharply capped
        compared with the undefended case.
    •   A p95 latency overhead that stays moderate under realistic top-k values.
    •   Ablations showing that write-time gate, retrieval gate, and propagation controller
        each matter.
    •   Scaling curves showing that the full pipeline remains stable as memory size and
        agent count grow.
If the only strong result is vector-store filtering, the paper is weak. If the powerful result is
shared-memory containment plus one other subsystem, the paper becomes much stronger.

Contributions
   •   We propose a framework-agnostic memory firewall for LLM agents that
       secures the write, retrieval, and propagation paths of agent memory rather than only
       the retriever or the prompt.
   •   We unify four practical agent memory subsystems—vector/RAG, semantic
       fact memory, episodic/example memory, and shared coordination memory—under
       a single provenance-aware defense schema and evaluation methodology.
   •   We introduce a scalable stress-evaluation harness for agent memory
       security that measures unsafe retrieval, contaminated context, propagation depth,
       utility preservation, and overhead across public agent frameworks.
   •   We show that memory defense must be evaluated as a scaling problem, not
       just an attack-success problem, by varying memory size, poison ratio, agent count,
       subsystem count, and retrieval top-k.

Final recommendation
The single strongest paper direction is:
    MemSieve: A Provenance-Aware Memory Firewall for LLM Agents
    A defense-first, public, cross-framework paper centered on write-time validation,
    retrieval-time risk gating, pre-tool verification, and propagation containment
    across four memory subsystems.
This direction is better than the main alternatives:

Alternative                      Why it is weaker now
Vector-store-only defense        Too easy to dismiss as another RAG paper.
Attack-only      memory          Violates your defense-first goal and is crowded by public
paper                            attack work.
Propagation-only multi-          Risks looking synthetic unless tied back to persistent shared
Alternative                    Why it is weaker now
agent paper                    memory and broader memory types.
Huge benchmark paper           Impossible to finish convincingly in two weeks.

The minimum viable version of the paper should be:

   •   LangGraph, LlamaIndex, CrewAI
   •   Vector/RAG, semantic, episodic, shared coordination memory
   •   No defense, provenance-only, spotlighting, trust-threshold sanitizer, full MemSieve
   •   Poisoned insertion, unsafe retrieval, contradiction collision, shared-memory
       cascade, flooding
   •   Clean utility table
   •   One ablation table
   •   Three scalability figures
   •   One primary model
The stronger version if time allows should add:

   •   AutoGen as a fourth framework
   •   Optional Letta/MemGPT archival/shared-memory case
   •   One second model
   •   Vector-row comparison with RAGForensics
   •   Tool-row comparison with Task Shield
   •   Small public benchmark subset if it plugs in cleanly
The harsh practical verdict is this: build the smallest paper that undeniably shows
cross-subsystem defense plus scaling. That paper is much more likely to survive
review than a broader but weaker project. The fastest way to kill the submission is to
overreach on frameworks, domains, or baseline reproductions. The fastest way to make it
publishable is to keep the claim narrow, the defense pipeline crisp, the metrics generic, and
the scalability evidence central.
Open questions / limitations: because the unpublished draft was not retrievable here, I
avoided overlap-specific judgments and built the roadmap entirely from public material. If
you later notice any accidental similarity in naming, scenario framing, or metric phrasing,
change those immediately before writing; your proposed paper is strong enough without
leaning on anything private.
